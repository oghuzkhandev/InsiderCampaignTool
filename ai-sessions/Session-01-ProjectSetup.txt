  Önerdiğim başlatma sırası:
  postgres (healthy) → migrate (tamamlanır) → seed (tamamlanır) → api, worker,
  mock-provider → web.
  migrate ve seed aynı backend imajından tek seferlik çalışan servisler olur,
  seed tekrar çalışınca kayıt çoğalmaz. Mock provider'ın
  mock_provider_acceptances tablosu migration'la geldiği için o da migrate'e
  bağlı.

  Sorular

  1. campaigns_test database'ini kim oluşturacak?
  - (a) Postgres init script'i. Yalnızca boş volume'de çalışır, volume varsa
    oluşmaz.
  - (b) make test içinde "yoksa oluştur" adımı ve ardından aynı migration'lar.

  Önerim (b). Mevcut volume'lerde de çalışır ve ADR-012 (DECISIONS.md#L152)'deki
  database adı korumasıyla aynı yerde durur.

  2. make test neyi ayağa kaldıracak?
  - (a) Yalnızca Postgres'i (docker compose up -d --wait postgres). Unit ve
    integration testleri çalışır. E2E testleri API, worker ve provider'ı Go
    testinden alt süreç olarak başlatır; böylece worker-kill testinde gerçek
    SIGKILL kullanılabilir.
  - (b) Tam compose stack'i.

  Önerim (a). Daha hızlı olur ve lease/backoff süreleri testte kısaltılabilir.

  3. Web nasıl servis edilecek?
  - (a) Vite dev server.
  - (b) Çok aşamalı build ile statik dosyaları nginx servis eder, /api aynı
    origin'den proxy'lenir.

  Önerim (b). Reviewer npm bilmeden docker compose up yapacak ve CORS sorunu
  olmaz. SSE için nginx'te proxy_buffering off gerekir, yoksa dashboard canlı
  akmaz.

  4. Portlar ve host'a açılanlar.
  Önerim hepsini yalnızca 127.0.0.1'e açmak: web 8080, api 8081, mock-provider
  8082 (admin/stats uçları testler için), postgres 5432. Makinende 5432'yi
  kullanan başka bir Postgres varsa söyle, 5433 yaparız.

  5. Temiz klonda .env yok.
  .env gitignore'da, yani temiz klonda docker compose up env_file: .env'i
  bulamayıp hata verir. Önerim compose'ta ${LLM_PROVIDER:-mock} gibi
  varsayılanlar kullanmak. Böylece .env olmadan MockLLM ile açılır.
  ANTHROPIC_API_KEY yalnızca api servisine geçer, worker'a girmez.

❯ Yaptıkların okey sadece queue_depth'i bir sayaç olarak mı düşündün ona göre

● Hayır, queue_depth'i sayaç olarak düşünmedim, o bir gauge: anlık değeri
  gösterir, artıp azalır. Sayaç (counter) ise sadece artar. Metrik türleri
  şöyle:

  ┌────────────────────────────────────────────────────┬────────────────────┐
  │                       Metrik                       │        Tür         │
  ├────────────────────────────────────────────────────┼────────────────────┤
  │ messages_sent_total, send_attempts_total{outcome}, │                    │
  │  stale_result_total, reaper_requeued_total,        │ counter            │
  │ llm_validation_failures_total                      │                    │
  ├────────────────────────────────────────────────────┼────────────────────┤
  │ queue_depth{channel}                               │ gauge              │
  ├────────────────────────────────────────────────────┼────────────────────┤
  │                                                    │ muhtemelen         │
  │ ratelimit_wait_seconds                             │ histogram (bekleme │
  │                                                    │  süresi dağılımı)  │
  └────────────────────────────────────────────────────┴────────────────────┘

  Bu ayrım, "worker'da mı API'de mi üretilsin" sorusunu etkiliyor. Ben §12 ve
  ADR-016'da hepsini "sayaç" diye yazdım. Bu queue_depth ve
  ratelimit_wait_seconds için doğru değil. Ayrıca queue_depth'i worker'a koymam
  bence yanlış oldu:

  - Counter'lar süreç belleğinde birikir, bu yüzden worker'da üretilmeleri
    zorunlu.
  - queue_depth ise belleğe bağlı değil, messages tablosundan hesaplanabilir
    (status='queued', kanala göre sayı). /metrics her okunduğunda tek bir
    indexli sorguyla üretilebilir.
  - Worker çökerse veya durursa onun /metrics ucu da gider. Kuyruğun biriktiğini
    en çok o anda görmek istersin, ama worker'a bağlı gauge tam o anda yok
    olur.

  Önerim: queue_depth'i API'nin /metrics ucuna taşıyalım ve her okunuşta
  veritabanından hesaplayalım. Worker'da yalnızca counter'lar ve histogram
  kalır.

  İstersen §12'yi ve ADR-016'daki "sayaç" ifadelerini bu ayrıma göre düzeltirim.
  Hangisini istersin?
